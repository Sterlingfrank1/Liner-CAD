> 范围：完成 `DESIGN.md` §10 的 M0–M3。§10 的“之后”一行（齿轮蜗杆、弹簧、轴承、钣金、焊接件等）是持续推进的工作，不在 v0.1 内；v0.2 的方向见第 6 节。

## 2. 里程碑生命周期

```
BRIEF（监督会话写）
  → SPEC（里程碑会话写；PR 合并即通过 Spec 门禁）
  → 卡片（GitHub issue，label `card`，挂到对应 milestone）
  → 逐卡 TDD 开发（一卡一 PR，评审后 squash 合并）
  → 里程碑验收（从干净 clone 跑 BRIEF 的验收场景，独立验证）
  → HANDOVER + tag
  → 监督会话复核，记入第 5 节 → 下一个里程碑
```

文档都放在 `docs/milestones/Mx/`：

| 文件 | 谁写 | 内容 |
|---|---|---|
| `BRIEF.md` | 监督会话 | 范围、验收标准、约束、留给 Spec 决定的问题、Goal 条件 |
| `SPEC.md` | 里程碑会话 | 详细设计：模块与接口、数据结构、验收项 → 测试 / 演示的映射、卡片清单、风险、偏离记录 |
| `HANDOVER.md` | 里程碑会话 | 交付了什么、怎么验证、证据、已知缺口、偏离与决策、待用户人工评审项、给下一里程碑的说明 |
| `evidence/` | 里程碑会话 | 验收日志、少量渲染图、Agent 对话修改的记录 |

**卡片**（GitHub issue）写清：目标、范围、接口、先写哪些测试、完成定义、执行档位（见第 4 节）、依赖的卡片。

## 3. 质量门禁

| 门禁 | 时点 | 通过条件 | 证据 |
|---|---|---|---|
| G1 Spec | 开发前 | SPEC 覆盖 BRIEF 的全部验收项，每一项都映射到测试或演示；卡片拆好；一个新上下文的 agent 独立评审一轮，意见已处理 | SPEC 的 PR |
| G2 Red | 卡片开工 | 先提交会失败的测试 | PR 里第一个 commit |
| G3 Green | 开 PR 前 | 全量 `pytest` 和 `ruff` 通过，新代码有测试覆盖，CI 通过 | CI 记录 |
| G4 Review | 合并前 | **只对核心卡片**：非作者的 agent 独立评审一轮，没有未处理的正确性问题。其余卡片 CI 通过 + 作者自查即可 | PR 正文或评论 |
| G5 Milestone | 交接前 | 从干净 clone 跑完 BRIEF 的验收场景；一个独立的验证 agent 复现结果；HANDOVER 写完并合并 | `evidence/` + HANDOVER |
| G6 监督复核 | 下一里程碑前 | 监督会话复核 G5 的证据，并在干净 clone 上抽查 | 第 5 节 |

原则：不接受“应该能用”；不为了通过而削弱检查或测试；失败要回到源头修。

## 4. 执行方式

- **Goal 模式。** 每个里程碑、每张卡片都写出可以独立评估的 Goal 条件（不超过 500 字符）。会话里能用 Claude Code 的 `/goal`（或 `ProposeGoal` 工具）时，用它设定里程碑 Goal；不能用时，Goal 条件就是硬合同：没满足就不结束回合，除非卡在只有用户才能做的决定上。
- **执行档位。**
  - 里程碑会话：Opus，负责设计、集成和门禁把关。
  - 核心卡片（数据模型、布局引擎、动作日志与重放、事务、HLR 对照、Viewer 桥）：Opus。
  - 简单卡片（数据表录入、CLI 薄封装、模板、范例、文档、补测试）：Sonnet 5.5 + xhigh（Agent 工具传 `model: "sonnet"`、`effort: "xhigh"`）。
  - 评审和验证：新上下文的独立 agent，只给原始材料，不给“预期答案”。
- **并行。** 互不依赖、不改同一批文件的卡片可以并行（子代理用 `isolation: "worktree"`）。同一文件不并行写。
- **人工评审。** `DESIGN.md` 中要求“人工评审 / 专家评分”的验收项，v0.1 先用多模态模型按评分表评审，结果写进 HANDOVER 的“待用户人工评审”一节，不阻塞推进。

### 4.1 精简规则（2026-11-08 起）

用户反馈 M0 开销过大。目标是保障核心功能和出图质量，不做过度防御性的设计。以下规则优先于前文：

- **代码只写当前验收需要的。** 不为不可能出现的输入写校验，不预留扩展点。错误处理放在 Agent 会碰到的边界上（Python API 入口、CLI），给出 ID、原因和候选；内部代码信任调用方。
- **测试以行为为主。** 每个验收项、每条主路径、真实会发生的关键边界各有测试即可；不写穷举式的参数校验测试。一张卡片的测试代码一般不超过实现代码。
- **评审只给核心卡片，一轮为限。** 核心卡片指数据模型、布局引擎、动作日志与重放、事务、HLR 对照、Viewer 桥；只看正确性和对 `DESIGN.md` 的偏离，不看风格。
- **PR 可以合并。** 堆叠的分支、几张简单卡片可以放进一个 PR 一起合并。
- **少开子代理。** 每开一个都要重新读一遍上下文。只在真正并行的大块工作和里程碑门禁的独立验证时用；实现优先交给 Sonnet。
- **文档写短。** SPEC、HANDOVER 只写决定、接口和证据，不写过程叙述。
- **不省的：** G5 里由独立 agent 只看 `SKILL.md` 完成的多轮对话修改、出图评审。这两项直接验证核心竞争力。

### 4.2 额度与自动续跑

账户是 Pro 计划，5 小时额度和每周额度都可能用完。里程碑会话额度用完时，把进度写进进度笔记，最后一条消息以 `Mx BLOCKED — usage limit` 开头。监督会话在每个 5 小时窗口重置后约 10 分钟自动检查一次：里程碑会话停了就让它从进度笔记继续；里程碑完成了就做 G6 复核并启动下一个。

## 6. v0.2 方向（v0.1 不做，但设计不能堵死）

| v0.2 方向 | 对 v0.1 设计的要求 |
|---|---|
| **图形效果和标注专业度的进一步强化**：更深入地内化资源库能力，用大量零部件图纸做评测 | 资源库按“机器可读、注明标准号、可批量扩充”组织；评测集和评测脚本能批量跑、能出汇总指标（一次通过率、违规数、修改轮数），加用例不改代码 |
| **3D 格式输出：STEP**，进一步表达产品制造信息 PMI | 尺寸、公差 / 配合、基准、形位公差、粗糙度的意图保持语义化（类型、数值、基准引用、所依据的标准分字段存放，不只拼成文字），并能关联到被测几何；这样 v0.2 才能映射到 STEP AP242 的语义 PMI。M3 引入的 3D 来源（build123d）也是 STEP 输出的基础 |
