# 评测指标方案：把“出图专业度”变成可验证的函数（讨论稿）

2026-11-10 · 状态：待决策，未开发 · 配套 `DRAFTING-COVERAGE.md` §2.4、`docs/ROADMAP.md` §6

## 0. 一句话

**指标 = 带标准号的谓词函数。** 每个指标是一个 Python 函数，输入图纸（语义模型 + 渲染图元），输出若干条 finding（元素 ID、规则、条款、实测值、期望值、候选修法）；benchmark 分数只是这些 finding 的归一化汇总。
同一套函数既是 `lcad check`（Agent 迭代时读的反馈），又是 benchmark（汇总成分数），又是将来后训练的可验证奖励。不另起一套“评分系统”。

对两个选项的回答：**函数 + 约束语义是评测本体；标准文献（含 GB/T 1182）是规则的来源，离线编译成函数，不在运行时 RAG。** RAG 回答的是“标准怎么说”，解决不了“这张图对不对”；后者必须是能执行、能复现的判定。

## 1. 三类判定（oracle），由便宜到贵

| 类 | 需要什么 | 判什么 | 例子 | 现状 |
|---|---|---|---|---|
| **R 规则**（无参考） | 只要图纸本身 | 普适的制图规定：违反即错 | 剖面线角度、轴线公差带加 Φ、形状公差不带基准、尺寸线间距、文字压线 | Checks 五个规则包 23 条 |
| **E 期望**（有参考） | 用例附带 `expect.py` 或 3D 模型 | 这个零件该有什么：功能要求、完整性 | Φ30H7 必须有；端面对 A 的垂直度 ≤ 0.02；HLR 线全覆盖 | `geocmp`、`completeness` |
| **J 评审**（多模态 / 专家） | 渲染图 + 是非题清单 | 暂时写不成函数的判断 | 主视图是否选了形状特征面；整体是否均衡 | render-review（1–5 分） |

原则：**能下沉到 R 就不放 E，能下沉到 E 就不放 J。** J 的每个稳定结论都是一条待编码规则的候选——这就是“训练 Harness”的方向（`DRAFTING-COVERAGE.md` §3）。J 只用是非题（“基准 A 是否标在功能面上？”），不用 1–5 总分，否则不可复现、不可迭代。

## 2. 统一的 finding 和指标记录

在现有 `_f()` 基础上补齐四个字段，使每条 finding 自带“为什么错、错多少、怎么改”：

```python
{
  "rule": "gtol.datum_required",        # 指标 ID，点分：族.规则
  "id": "G3",                           # 元素 ID（可 @、可在 Viewer 着色）
  "clause": "GB/T 1182-2018 表2",       # 条款，来自规则目录
  "severity": "error",                  # error=硬门槛  warn=扣分  info=提示
  "measured": {"datum_refs": []},       # 实测
  "expected": {"datum_refs": ">=1"},    # 期望
  "candidates": ["A", "B"],             # 可选的修法 / 候选值
  "message": "垂直度是方向公差，必须注基准",
}
```

每条规则同时报告 **机会数**（opportunities：它检查了多少个对象）。于是任何规则都能归一成通过率 `1 - 违规数 / 机会数`，不同大小的图纸可以直接比较，避免“标得少就违规少”。

## 3. 指标体系

两个维度切：**对象层级**（特征 / 零件 / 视图 / 装配）× **指标族**。下面每一行都是一个或几个函数；★ 为已有，其余为新增。

### 3.1 G 图形（画得对不对）

| ID | 指标 | 判定函数要点 | 类 |
|---|---|---|---|
| G.geo | 几何覆盖 | 每个视图，图元 vs HLR 投影：召回（漏线）、精度（多线），分可见 / 隐藏线 ★ | E |
| G.linetype | 线型正确率 | 匹配上的每条边：可见粗实线、不可见虚线、轴线 / 对称线点画线、牙底细实线 | E |
| G.align | 投影关系 | 长对正、高平齐、宽相等 ★ | R |
| G.conv | 规定画法 | 每条规定画法一个谓词，**在渲染图元上判**（不是在工具 intent 上判，否则是自证）：外螺纹牙底细实线、端视图约 3/4 圈；分度圆点画线；肋板纵剖不画剖面线；相邻零件剖面线方向或间距不同；实心件纵剖不剖 | R |
| G.section | 剖视一致性 | 剖切符号、名称、箭头与剖视图成对；剖面区域闭合；同一零件各剖视剖面线一致 ★部分 | R |
| G.express | 表达充分 | 每个 3D 特征至少在一个视图中以可见线（或剖视）出现；不必要的虚线数；可省略的重复视图数 | E |
| G.layout | 布局 | 重叠、出框 ★；视图间距 ≥ 标注所需；图幅利用率在区间内；视图包络不压标题栏 | R |

### 3.2 D 尺寸与标注（标得全不全、对不对）

| ID | 指标 | 判定函数要点 | 类 |
|---|---|---|---|
| D.complete | 完整性（召回） | 由 3D 特征 / `expect` 推出应有的定形、定位、总体尺寸，逐条看是否被覆盖 ★ | E |
| D.redundant | 冗余（精度） | 重复尺寸、封闭尺寸链 ★ | R |
| D.value | 数值一致 | 尺寸值 = 被标几何的实测值（容差 0.01）；改了几何没改尺寸会被抓到 | R |
| D.fit | 公差与资源库一致 | Φ30H7 的偏差 = 资源库查表值；配合代号合法；未注公差有注明 ★部分 | R |
| D.chain | 尺寸链 | 闭环可解，封闭环公差 = 组成环之和（极值法）或在声明范围内 ★部分 | R |
| D.place | 排布可读性 | 尺寸线互相交叉数；尺寸线与轮廓线交叉数；平行尺寸间距 ≥ δ、小尺寸在内大尺寸在外；尺寸界线超出 2–3 mm、与轮廓留隙；文字方向（水平尺寸字头朝上、垂直尺寸朝左）；文字与任何图元不重叠；箭头大小一致 | R |
| D.group | 集中标注 | 同一特征的尺寸集中在一个视图；尽量标在反映形状特征的视图上；避免标在虚线上 | R/J |

### 3.3 T 几何公差、基准、粗糙度、技术要求（GD&T / PMI）

| ID | 指标 | 判定函数要点 | 类 |
|---|---|---|---|
| T.syntax | 公差框格语法 | 特征项目 × 基准要求 × 公差带形状 × 允许的修饰符（Ⓜ Ⓛ Ⓔ Ⓟ CZ…）按 GB/T 1182 表格判 ★部分 | R |
| T.datum | 基准体系 | 引用的基准都已定义 ★；基准字母禁用集 ★；基准顺序（第一 / 二 / 三基准）不重复；基准标在实际可用作基准的要素上 | R/E |
| T.target | 被测要素语义 | 引线箭头落在轮廓或界线上 = 表面；与尺寸线对齐 = 轴线 / 中心面；这个几何含义必须等于语义模型里的 `target`。把“标注细节”变成可判定的语义一致性 | R |
| T.hier | 公差递进 | 同一要素：形状 ≤ 方向 ≤ 位置 ≤ 尺寸公差；跳动 ≥ 对应的圆度 / 同轴度 | R |
| T.rough | 粗糙度 | 符号语法 ★；配合面 Ra 与 IT 等级匹配 ★部分；其余表面有统一注法 ★ | R |
| T.func | 功能要求 | `expect` 中声明的关键公差、基准、粗糙度、技术要求条文是否出现且数值不宽于要求 | E |
| T.sem | 语义化率 | PMI 中以语义元素（带类型、数值、基准引用、被测要素）表达的比例；自由文字形式的公差计为 0。这是 STEP AP242 的前提 | R |

### 3.4 A 装配

序号引线不交叉、序号沿水平 / 竖直线对齐且间距 ≥ δ、顺时针或逆时针连续；明细栏与组件一一对应、相同零件合并；装配尺寸（配合、安装、外形、性能）四类是否齐全（E）；相邻件剖面线区分（与 G.conv 共用）。

### 3.5 P 过程（Agent 迭代体验）

一次通过率、到零 error 的修改轮数、每轮耗时 / token、每条 finding 的修复率（下一轮消失的比例）、回归率（修好的又回来）。这是 harness 相对“裸写 ezdxf”的主要优势，必须在 benchmark 里有一席。

### 3.6 汇总

- **门槛**：error 数必须为 0，否则该图该族记“不通过”。
- **分数向量**：每族一个 [0,1]：G、D、T、A 各自 = 该族各规则通过率按机会数加权；P 单列。不压成单一总分（单分会掩盖“图好看但标错了”），需要排名时再给一个固定权重的总分作参考。
- **切面**：按对象层级、零件族、标准（GB / ISO）、用例来源（自建 / 公开 / 客户）分别出。

## 4. 约束语义：`expect.py`

这是用户设想的“把评测细节写成函数 & 约束语义”的具体形态。用例的期望用**和画图同一种风格的 Python** 写，Agent 和客户都会写：

```python
# evals/L2/shaft/output_shaft/expect.py
def expect(e):
    bore = e.feature(cyl=30)                     # 按几何签名找要素，不依赖元素 ID
    e.dim(bore, fit="H7")                        # 必须有，且配合为 H7
    e.datum("A", on=bore, axis=True)             # 基准 A 是这根轴线
    e.gtol("perpendicularity", on=e.face("end_left"), datums=["A"], max=0.02)
    e.rough(bore, ra_max=1.6)
    e.note(contains="调质")                       # 技术要求条文
    e.view("front", section=("full", "half"))    # 允许多种正确答案
    e.any_of(e.gtol("runout", on=bore, datums=["A"]),
             e.gtol("coaxiality", on=bore, datums=["A"]))
```

要点：

1. **按几何签名匹配，不按 ID。** `cyl=30` 找到直径 30 的圆柱特征及其在各视图的投影；3D 来源用 `src3d` 面引用。这样任何 Agent、任何画法都能被同一份 `expect` 评判。
2. **专业答案不唯一。** `any_of`、取值区间（`max=`）、`must / should` 两档，避免把参考图当唯一答案。
3. **期望写“要什么”，不写“怎么画”。** 怎么画由 R 类规则管；`expect` 只承载零件特有的功能要求，因此每个用例只有十来行。
4. 客户加用例 = 加一个目录（`req.md` + `model.py` 或参考图 + `expect.py`），不改代码；企业标准 = 加一个规则包（第 6 节）。

## 5. 标准的内化：编译，而不是检索

以 GB/T 1182-2018（等同 ISO 1101:2017）为例。它的核心是几张表和一组图示规则，正好能编译成数据 + 谓词：

1. **数据表** `res/gtol.toml`：19 个特征项目 → 类别（形状 / 方向 / 位置 / 跳动）、是否必须有基准、允许的被测要素类型、公差带形状、允许的修饰符；每行注明条款号。
2. **规则目录** `rules/catalog.toml`：每条可判定的条文一行——`id、条款、陈述、函数名、状态（已实现 / 仅 J / 待做）、正例与反例 fixture`。例：

   ```toml
   [[rule]]
   id = "gtol.datum_required"
   clause = "GB/T 1182-2018 表2"
   statement = "方向、跳动公差必须注基准；形状公差不得注基准"
   fn = "gtol_datum_required"
   status = "done"
   ```

3. **条款覆盖率** = 状态为 done 的条款 / 该标准可判定条款总数。这本身就是一个可报告的指标：“GB/T 1182 已内化 63%”。
4. **一次性抽取流程**：PDF 全是图片，由一个开发期会话用多模态逐页读，产出目录草稿（条款、陈述、示例图里的对 / 错）；人工复核后逐条实现函数。原文不入库（版权），只入条款号、陈述摘要和数值。本机缺 poppler，读 PDF 需先装或先转图片。
5. RAG 的位置：开发期辅助写规则、给 Agent 的 finding 附条款摘要；不参与判分。

## 6. 让指标本身可信：变异测试

指标是函数，函数也会错。用**缺陷注入**验证指标，同时批量造用例：

1. 取一张通过的参考图，按变异算子注入已知缺陷：删一个尺寸、把基准 A 改成未定义的 D、去掉 Φ、把可见线改成虚线、把尺寸文字挪到与轮廓重叠、给形状公差加基准、把 H7 偏差改错……
2. **指标检出率** = 被正确报告的注入缺陷 / 注入总数；**误报率** = 对参考图的 finding 数。每条规则上线前要求检出率 1.0、误报 0。
3. 同一批变异图就是 **修复任务**：给 Agent 一张带缺陷的图 + `lcad check` 输出，看它几轮修好。这直接测“Agentic 迭代”，而且答案已知。

变异算子是有限的、按规则成对写的（每条规则配一个“破坏它”的算子），可以随规则目录一起增长。

## 7. 与自我进化 / 后训练的关系

每次运行留一条轨迹：`任务 → 脚本 → finding → 修改 → 新 finding → 分数`。因为分数来自确定的函数，这就是**可验证奖励**：

- 对 Harness：J 类的稳定结论和高频 finding → 新规则、新工具、卡片修订（现有闭环）。
- 对模型（v0.2 以后，可选）：轨迹可直接用于 SFT / RL，奖励不依赖人工打分；变异修复任务是天然的大规模训练题。
- 对客户：他们的 `expect.py` 和企业规则包就是他们的私有 benchmark，数据留在他们那里，格式与我们一致。

## 8. 落地顺序（建议，每步一个 PR）

| 步 | 内容 | 产出 |
|---|---|---|
| 1 | finding 补 `clause / measured / expected / candidates`，规则报告机会数；`run.py` 输出分族分数向量 | 现有 40 例出第一份基线向量 |
| 2 | 规则目录 `catalog.toml` + 变异框架；给现有 23 条规则补正反例与变异算子 | 指标检出率 / 误报率 |
| 3 | `expect.py` 与几何签名匹配；为 L2 的 20 例写 expect | E 类功能指标 |
| 4 | GB/T 1182 抽取 → `res/gtol.toml` + T.syntax / T.target / T.hier | 1182 条款覆盖率 |
| 5 | D.place 排布指标（交叉、间距、嵌套、文字方向）——对准 v0.1 的头号缺口“尺寸排布避让弱” | 排布分数，可与 render-review 对照校准 |
| 6 | 仅 DXF 模式：只用渲染图元能判的规则（G.layout、D.place、G.conv 的一部分），用于裸 ezdxf 基线和客户导入图纸 | 可与任意来源的图纸比较 |

第 1、2 步不加新判断，只是把现有能力变成可比较、可信的数字，建议先做。

## 9. 不做的事

- 不做“像素级 / 图像相似度”评分：同一张合格图纸有许多正确排法，相似度惩罚的是差异而不是错误。
- 不做单一总分驱动的优化。
- 不让 LLM 在运行时打分进入门槛；J 只做发现和抽检。
