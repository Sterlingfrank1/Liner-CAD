# v0.1.3 拆卡方案（CARDS）v2 —— 3 个 PR

- 版本：v2.0（按复核意见合并：10 张卡 → 3 个 PR）
- 配套：`v0.1.3-REQ.md`、`v0.1.3-SPEC.md`
- 开发：agy cli（Orchestrator：Neon xhigh + Hydrogen xhigh）
- 监控：DSH（只读）
- **发布：agy 执行 `scripts/release.py 0.1.3`（打 tag + Release），DSH 事后核对**
- 总规模：约 **12–15 人日**（含测试与收口）

## 0. 为什么是 3 个 PR，而不是 10 张卡

上一版按“技术改动点”切了 10 张卡，管理成本高、评审也碎。按**业务域**合并：

- **PR-1 Viewer 全量**：开关/端口、面板、框选、选择集、标题栏点选、下载——都是“看图/点图”一件事，同文件同测试面，评审一次就够；
- **PR-2 项目模板**：保存/固化/实例化/自检——一条完整业务链；
- **PR-3 样式与 Logo**：表格与标题栏的可配置能力，依赖 PR-1 的点选。

这与 agy 最初的 PR-1（REQ-2+3+4+5 合一个 PR）是同一思路，只是把“标题栏点选/下载”也归进 Viewer 域。

| PR | 分支 | 内容 | 估时 | 依赖 |
|---|---|---|---|---|
| **PR-1** | `v013/viewer` | R1–R8（Viewer 全量） | 3.5–4.5 天 | — |
| **PR-2** | `v013/templates` | R9–R12（项目模板 + 自检） | 4–5 天 | PR-1（验收复用下载截图） |
| **PR-3** | `v013/style-logo` | R13–R15（样式 + Logo） | 3–4 天 | PR-1（点选） |
| **PR-4** | `v013/release` | R16（版本号、发布说明、HANDOVER、ROADMAP、全局安装验证） | 0.5 天 | PR-1/2/3 全部合入 |

## 4. 顺序与门禁

```
PR-1 ──► 门禁（首图 / 框选 / 点选 / 下载 四场景）
  │
  ├──► PR-3（样式依赖点选）
  │
  └──► PR-2（模板，可与 PR-3 并行）
           │
           └──► PR-4 收口（版本号/发布说明/HANDOVER/ROADMAP）──► DSH 执行 release.py 0.1.3
```

- PR-1 合入并经用户确认“用起来顺手”后再开 PR-2/PR-3；
- PR-2 与 PR-3 可并行（两个分支、两个 PR），都基于 PR-1 合入后的 main；
- 每个 PR 合并前：`pytest` + `ruff` 全绿；PR-1/PR-3 再跑 `evals/run.py --baseline`。
- PR-4 合入后，`main` 必须全绿且 `scripts/release.py 0.1.3 --dry-run` 通过；**正式发布由 agy 执行**，DSH 事后核对 tag 与 Release。

## 6. 纪律

1. 一个 PR 一个分支，squash 合并；PR 描述贴验收清单与证据。
2. 先写失败测试。
3. 契约只增不改；新增字段在 PR 描述里列出。
4. SPEC 没写死的选择 → **停下来问用户**（DSH 只读，不决策）。
5. 文档与代码同 PR。
## 7. 卡（issue）与 PR 的关系与建议

**两者不是一回事，职责不同：**

| | 卡（GitHub issue） | PR |
|---|---|---|
| 回答 | **做什么、为什么、算不算完成**（目标 + 验收清单 + 风险） | **怎么改、改得对不对**（diff + 测试 + 评审） |
| 载体 | 里程碑看板、状态、验收证据、交接记录 | 代码、CI、review comment |
| 生命周期 | 建卡 → 开发 → 验收 → 关卡 | 开分支 → 提交 → 评审 → squash 合并 |
| 关联网 | 被 PR 的 `Closes #N` 引用，合并后自动关闭 | 合并 commit 带 `(#N)`，可回溯 |

**建议：开 3 张卡，与 3 个 PR 一一对应。** 理由：

1. 这个仓库的门禁与交接是按 issue 组织的——ROADMAP 看板、G5 验收证据、HANDOVER 都引用卡号；没有卡，里程碑收口时拿不出"哪些做完了"的清单。
2. 你（用户）不读 diff，只看卡上的验收勾选就能判断进度；DSH 只读监控时，也以卡为核对单位。
3. 卡还是"停止线"：agy 遇到 SPEC 没写死的选择，在卡里提问，不自行扩大范围。

**不要**为每个 commit 开卡，也不要 10 张小卡——就 3 张，卡体直接用本文件各 PR 的"目标 / 范围 / 验收"三段。

操作顺序：建里程碑 `v0.1.3` → 建 3 张 issue（贴本文件对应段落）→ PR 描述写 `Closes #<卡号>`。
